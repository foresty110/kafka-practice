[현재 상태 분석]
- 파티션은 3개가 존재하며 paymentId로 이벤트를 발행하고 있다.
- product-ranking,payment-history,delivery로 총 3개의 컨슈머 그룹과 각 그룹마다 한개씩 컨슈머를 가지고 있다.

[현재 상태의 문제점] 
- 이벤트 처리 성능 저하 
  병목현상이 발생할 수 밖에 없다. 하나의 컨슈머가 모든 파티션을 담당하기 때문에 하나의 파티션에서 처리가 오래걸릴 경우 나머지 파티션의 모든 이벤트 처리는 무한 대기 상태가 된다. 
- 리밸런싱으로 인한 중복처리 또는 데이터 유실
컨슈머가 다음 poll()을 호출하지 않고도 기다리는 최대 시간을 max.poll.interval.ms로 설정하는데
이 시간을 초과하면 해당 컨슈머가 죽었다고 판단하고 리밸런싱이 발생한다. 이 과정에서 같은 메세지를 다시 처리하거나 혹은 처리가 되지 않았음에도 다음 메세지를 처리하게 될 수가 있다.

[ 구조 개선 방법 ] 
파티션의 개수만큼 컨슈머 개수를 맞춰준다. 이 방법을 선택한 이유는 1:1 매칭이 되어야 병렬처리가 되므로 가장 효율적인 형태가 될 수 있기 때문이다. 
단, 현 상태는 결제 완료 토픽에 paymentId로 상태가 변화하지 않는 즉 순서를 보장하지 않아도 되는 이벤트만 존재하므로 파티션과 컨슈머의 개수를 맞추는 것이 가능하나 
순서를 맞춰 주어야하는 설계라고 하면 단순히 컨슈머 개수를 늘리는 방법은 적절하지 않다. 왜냐하면 파티션 개수를 늘리면 이미 저장되어있던 순서가 깨지는 동시성 이슈가 발생할 수 있기 때문이다 
따라서 배송상태가 변경되는 메세지를 처리해야한다면 토픽을 분리하고 컨슈머 개수를 맞추는 것만을 고려하는 것이 아닌 id기준으로 키값을 설정하는 것을 함께 고려한 설계가 필요할 것이다.
